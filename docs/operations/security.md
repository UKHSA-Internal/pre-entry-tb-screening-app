## Secrets management

### Local development secrets

Secrets for local development are stored in `configs/.env.local.secrets`. This file is:

- **Never committed** — it is listed in `.gitignore`
- Generated by running `pnpm pull:secrets` (requires AWS credentials)
- Pulled from **AWS Secrets Manager** in the `pre-entry-tb-screening-nl-develop` account

To pull secrets:

```sh
# Set AWS credentials first (via Halo)
pnpm pull:secrets
```

### Environment-specific secrets

Each deployment environment has its own secrets stored in AWS Secrets Manager. They are injected as Lambda environment variables at deploy time via the CDK stack.

Do not hard-code secrets in source code, configuration files, or comments.

### Git Secrets

The project uses `git-secrets` to prevent accidental commits of AWS credentials and other sensitive patterns. It is configured as a pre-commit hook.

If you trigger a false positive, investigate before bypassing — do not use `git commit --no-verify` unless you have confirmed the flagged content is safe.

### Secret rotation

Secrets should be rotated regularly. When rotating:

1. Update the value in AWS Secrets Manager for each environment
2. Re-deploy the relevant environment(s) to pick up the new secret
3. Verify that the service continues to function after rotation

## IAM roles and access

### AWS account access

Access to AWS environments is managed via IAM roles and requested through ServiceNow. See [docs/aws-access.md](../aws-access.md) for the request process.

Short-lived credentials are obtained via [Halo](https://halopr.awsapps.com/start/#/?tab=accounts). Do not use long-lived access keys.

### Lambda execution roles

Each Lambda has a least-privilege IAM execution role. Roles grant access only to the specific DynamoDB tables, S3 buckets, SQS queues, and Secrets Manager secrets the Lambda requires.

If a Lambda needs access to a new resource, update the IAM role in the CDK stack and follow the PR review process — do not grant `*` permissions.

## API authentication

All API Gateway endpoints are protected by a TOKEN authoriser Lambda that validates Azure B2C JWTs.

- Tokens are validated against the configured B2C tenant, client ID, and policy
- The `clinicId` claim is extracted and forwarded to downstream Lambda handlers
- Requests without a valid token receive `401 Unauthorized`
- Requests with a valid token but insufficient permissions receive `403 Forbidden`

See [docs/backend-services/authoriser/README.md](../backend-services/authoriser/README.md) for authoriser details.

### Token handling

- Never log full JWT tokens — use `logger.info` with only safe, non-sensitive fields
- Never store tokens in DynamoDB or S3
- Token expiry is enforced by the B2C authoriser

## Dependency security

### Automated updates

[Renovate](https://docs.renovatebot.com/) runs nightly and opens PRs for dependencies with security updates. These PRs should be reviewed and merged promptly.

### Manual review

Before merging any PR that updates dependencies:

1. Check the release notes for breaking changes
2. Verify the update does not introduce a known CVE (check npm advisories or Snyk)
3. Ensure all tests pass after the update

### Running a security audit

```sh
pnpm audit
```

Address any high or critical severity vulnerabilities before deploying.

## Security checklist for deployments

Before deploying to `preprod` or `prod`:

- [ ] No secrets or credentials are present in the diff
- [ ] All Lambda IAM roles follow least-privilege
- [ ] Input validation is present on all new API handlers
- [ ] No new `*` wildcard permissions have been added to IAM policies
- [ ] Dependency security audit has been run (`pnpm audit`) with no high/critical findings
- [ ] JWT validation has not been weakened or bypassed
- [ ] `git-secrets` hooks are in place and passing
- [ ] Environment-specific configuration is correct for the target environment
